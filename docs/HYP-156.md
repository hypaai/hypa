## Live translation endpoint

The ticket names `/v2/developer/translate`. It does not exist in either repo (`hypa-v2` calls it `/v2/developer/mt`), and `hypa` has no developer controller. The endpoint available here is `POST /v2/translate/mt` (`@hypa/translate-core` `mt`), which the Translate tab uses:

- Speed (measured 2026-10-31 against the local API): `provider: "auto"` took 6 to 8 s per line, of which the model call was 1.6 s. From this machine a Redis read takes about 208 ms, and the Auto router read one cooldown key per plan entry in sequence, plus the benchmark query (140 to 360 ms) on every call. `AutoRouterService` now reads the cooldown keys in parallel and caches the benchmark rows for 60 s: Auto over HTTP dropped to 1.0 to 1.6 s.
- Lens socket: `ws(s)://<api>/v2/agent/lens` (`LensSocketService`, plain `ws` server on the Nest HTTP server; `DelayedWsAdapter` skips this path). Auth reuses `AuthGuard` on the upgrade request (optional `Authorization: Bearer`; the guard lists `GET /v2/agent/lens` with the anonymous-allowed product routes), and each line goes through `TranslateController.translateText`, which resolves the user's API key the same way as HTTP. Client sends `{ type: 'translate', id, text, target }` (or `cancel`), server answers `{ type: 'translation', id, text }` or `{ type: 'error', id, message }`. Each line runs the same Auto path as `POST /v2/translate/mt` (no history, no client request id, so no progress or resolution writes), up to 6 at a time per socket. Four lines came back in 2.3 s together. The app falls back to the HTTP call for 30 s when the socket never opens (a server without it), and reports offline after repeated reconnect failures.
- `LiveLines` waits 250 ms for a stable line and treats OCR misreads (80% similar) of a pending or translated line as the same line. A captured line shows a spinner until its translation arrives.
- Accepts anonymous callers (`resolveProductCaller`); `provider: "auto"` with an empty or `auto` `source_lang` auto-detects.
- One `text` per call, server-sent events. No batch input.
- Writes a Translate history row for every signed-in call (`TranslateService.recordProductTranslation`). **Done:** `save_history: false` on the request skips the save; Lens always sends it.

## Camera and on-device OCR

- `react-native-vision-camera` 5.2.4 (published 2026-10-29), `react-native-nitro-modules` 0.37.1, `react-native-nitro-image` 0.15.2, `react-native-worklets` 0.7.4 are installed. The New Architecture and Hermes are on.
- Vision Camera ships no text recognition.
- `useFrameOutput` (frame processors) needs `react-native-vision-camera-worklets`, which is **not installed**. Calling it throws `Cannot use Frame Processors`.
- Native permissions already exist from `expo-image-picker`: iOS `NSCameraUsageDescription` and Android `CAMERA`. The iOS text only mentions chat photos; update it to cover Lens.
- `ios/` and `android/` are committed, so EAS builds from them and `app.json` plugin changes do not reach native builds on their own. Do not run `expo prebuild --clean`: it would drop the Podfile deployment-target fix.

OCR plugins checked on npm:

| Package | Supports VC 5 | Notes |
| -- | -- | -- |
| `vision-camera-ocr-plugin` 5.0.12 | Yes (>= 5.1, Nitro >= 0.36) | ML Kit on both platforms, Latin script only. `useTextRecognitionOutput` is a camera output: no worklets, results on the JS thread. Its frame-processor path needs `react-native-worklets-core` and can crash on Android with Nitro <= 0.37. Output boxes are in upright image space; `currentResolution` is sensor-native (axes swapped in portrait), so we map boxes ourselves. |
| `react-native-vision-camera-ocr-plus` 2.1.1 | Yes | Needs `react-native-worklets` >= 0.8; we have 0.7.4 (pinned with Reanimated 4.2.1). |
| `react-native-vision-camera-mlkit` 2.0.1 | Yes | Peer `@expo/config-plugins` ^57; Expo SDK 55 ships an older one. |
| `@bear-block/vision-camera-ocr` | No (VC 3 and 4) | |

**Decision: follow the ticket** (frame processor; Apple Vision on iOS, ML Kit on Android):

- Overlay alignment: the frame processor gets Vision Camera's exact frame-to-preview conversion (`frame.convertFramePointToCameraPoint`, then the preview's `convertCameraPointToViewPoint`). The output-only plugin path has no such helper; its own README says to use the frame processor for pixel-accurate overlays.
- iOS: Apple Vision ships with iOS (no extra model in the app) and runs on the Neural Engine.
- Battery: the frame processor can drop frames down to about 5 fps before OCR runs.

What it costs:

- Install `react-native-vision-camera-worklets@5.2.4`. It was built against `react-native-worklets` 0.9.1; we have 0.7.4 (held by Reanimated 4.2.1). 0.7.4 exports the APIs it uses (`createWorkletRuntime`, `scheduleOnRuntime`), but native compatibility is only proven by a dev build on both platforms. That build is the first gate.
  - **Gate result (2026-10-31):** installed, pinned at exactly 5.2.4. iOS first failed: the `RNWorklets` 0.7.4 header `WorkletsMessageThread.h` imports `<React/RCTMessageThread.h>`, which a module import cannot find with prebuilt React Native core (it lives under `React_Core/`). Worklets 0.9 deleted that header. `patches/react-native-worklets@0.7.4.patch` falls back to `React_Core/`. With the patch, `VisionCameraWorklets` builds for the iOS simulator and for Android (`arm64-v8a`). Still to do: a full dev-client build and run on real devices. Drop the patch when Reanimated and worklets are upgraded.
- Write a local Nitro module, `n-modules/hypa-lens-ocr`. It must be a Nitro module, because Expo modules cannot be called from the frame-processor thread. Return flat values, and create the frame output once with stable options, to stay clear of the Nitro <= 0.37 worklet-thread data race (margelo/nitro#1705).
- Fallback if the gate fails: `vision-camera-ocr-plugin` output mode, with our own box mapping.

**OCR module (2026-10-31):** `apps/hypa-intelligence-mobile/n-modules/hypa-lens-ocr`, linked like `hypa-keyboard-storage`. Modelled on VisionCamera's `react-native-vision-camera-barcode-scanner` 5.2.4; bindings generated with `nitrogen` 0.37.1 (an app dev dependency). `nitrogen/generated` is not in git: `pnpm install` (postinstall), `pnpm ios` / `pnpm android` and `pnpm generate:nitro` regenerate it, and the podspec and `build.gradle` run nitrogen themselves if it is missing. Run `pnpm generate:nitro` after changing `src/specs`.

- `startRecognition(frame)` copies or retains the frame's pixels and runs OCR on a background thread (returns `false` while busy); `takeRecognition()` returns the finished result once, else `''`. OCR must not hold the frame: CameraX does not deliver the next frame until the current one is closed, which would stop motion tracking. A result is a JSON string of `{ text, corners }` lines. `corners` is `[x0, y0, … x3, y3]`: top-left, top-right, bottom-right, bottom-left in reading order, normalized 0..1 in the upright image with the origin top-left. It is a string on purpose: struct conversion on the frame-processor thread races in Nitro <= 0.37 (margelo/nitro#1705). Keep it a string until Nitro is upgraded.
- iOS: Apple Vision `VNRecognizeTextRequest`, `.accurate`, language correction on, automatic language detection on iOS 16+, `minimumTextHeight` 0.0125 (the default 1/32 skipped small lines). Android: ML Kit `text-recognition` 16.0.1 (Latin).
- **Do not chain VisionCamera's converters for the overlay.** On iOS, `frame.convertFramePointToCameraPoint` returns upright coordinates, but the preview's `convertCameraPointToViewPoint` expects AVFoundation capture-device points (sensor landscape). Chaining them turned every box by 90° on the first device test (2026-10-31).
- Placement: the worklet maps three upright basis points into the preview's camera space: on Android through `frame.convertFramePointToCameraPoint` (sensor pixels, crop included), on iOS as raw-buffer 0..1 points (`uprightToFramePoint` divided by the frame size), which is AVFoundation's capture-device space. Passing upright points on iOS turned every box 90° and moved it (device test 2, 2026-10-31: vertical text drawn upside down at the wrong place). `lens.tsx` sends the three points through `convertCameraPointToViewPoint` once, and every corner is then mapped with that affine basis. `lineShape` gives centre, length, thickness and angle.
- Motion: `trackMotion(frame)` runs on every frame. It block-matches a 160-column luma grid against the previous frame (three-level pyramid, ±288 px per frame at 1920 wide, V-fit sub-pixel; about 0.5 px error in a synthetic test) and returns the shift in raw 0..1 frame units. The worklet adds it, turned upright (`frameToUprightVector`), to a cumulative `motion` synchronizable. OCR corners are stored in world coordinates (corner minus the motion when that OCR frame was taken). The overlay container is translated on the UI thread every display frame (`useFrameCallback` reads `motion`), so text follows hand shake without waiting for OCR or the JS thread. The worklet also keeps a smoothed velocity, and the overlay is drawn ahead by the time since that frame plus 55 ms: device test 3 measured the overlay about 75 ms behind the preview. Translation only: rotation and zoom are corrected by the next OCR result.
- Lines: `trackLines` matches each OCR result to the previous lines (same or similar text, nearby), keeps a line where it is when a new reading lands within 0.25% of the image (OCR jitter), otherwise moves it straight to the new reading, and keeps a line for 800 ms when OCR misses it. Each tracked line has a stable id (the overlay key). Device test 4 showed the old partial smoothing (20% per pass) left lines half a line off for seconds after a move; the overlay now glides each correction over 140 ms instead.
- iOS orientation for Vision: VisionCamera `left` maps to `CGImagePropertyOrientation.right` (and `right` to `.left`), matching the clockwise turn `uprightToFramePoint` uses.
- Colours: frames are RGB (`pixelFormat: 'rgb'`: BGRA on iOS, RGBA on Android). `lib/lens/line-colors.ts` splits samples in and around each line into two brightness groups; the group most of the border belongs to is the patch colour (so a neighbouring line or ornament does not turn it grey), the other is the ink. The share of ink inside the line picks regular, medium or bold. Patches are the OCR quad plus 10% of the line height above and below and 15% at each end (Vision boxes clip ascenders and descenders), with a thin feathered edge (`boxShadow`, 12% of the line height). Font size is 1.2 × box height for all-caps lines (Vision boxes hug capitals) and 0.9 × otherwise. `lib/lens/frame-points.ts` maps the upright corners to raw buffer pixels for that sampling (tested against VisionCamera's iOS matrix).
- The overlay draws a line only once it is translated and the translation differs from the original, so names and numbers stay as the real camera image. An all-caps source line gets an all-caps translation.
- Builds for the iOS simulator and for Android `arm64-v8a`. Still to check on real devices: boxes line up with the text (including ML Kit's upright coordinates on Android), and `.accurate` speed. Fall back to `.fast` if it is too slow.
